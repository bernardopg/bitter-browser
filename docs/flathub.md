# Submitting Bitter Browser to Flathub (owner task)

Tracked as DIST-05 in [TASKS.md](../TASKS.md). The owner does this by hand:
Flathub's [generative AI policy](https://docs.flathub.org/docs/for-app-authors/requirements)
forbids AI-written Flathub manifests, AI-opened or automated submission pull
requests, and AI-written commit messages, descriptions or replies in them.
Submitters must disclose AI-generated material in the app and its packaging.
Agents keep the upstream metadata (desktop file, metainfo, icons, the
`browser.bebitterbebetter.com.br` domain) ready; they never write the
Flathub manifest or the submission.

## What is already in place

- Application ID `br.com.bebitterbebetter.browser.Bitter`; Flathub verifies
  it against `browser.bebitterbebetter.com.br`, which the project controls.
- Metainfo that passes `appstreamcli validate`, with screenshots, release
  notes, branding colors and `<replaces>` for the old ID.
- Icons in every hicolor size, a symbolic icon and the MPL-2.0 license.
- The *Website* workflow publishes `site/.well-known/org.flathub.VerifiedApps.txt`.

## Steps

1. Wait for a release without known Flatpak bugs (0.6.1 or newer).
2. Fork `flathub/flathub` and create a branch from `new-pr`. The pull request
   targets `new-pr`.
3. Write `br.com.bebitterbebetter.browser.Bitter.yml` (or `.json`) at the root
   of the fork yourself. Use `flatpak/br.com.bebitterbebetter.browser.Bitter.json`
   in this repository as a reference, with two differences:
   - the source is the release archive
     `https://github.com/bernardopg/bitter-browser/releases/download/vX.Y.Z/bitter-browser-X.Y.Z.tar.gz`
     with the sha256 from the release's `bitter-browser-X.Y.Z-sha256.txt`;
   - the Rust crates come from `cargo-sources.json`, generated by a tool
     (Flathub accepts tool-generated sub-manifests):
     `flatpak-builder-tools/cargo/flatpak-cargo-generator.py Cargo.lock -o cargo-sources.json`
     run on the release tag.
4. Keep only the permissions a browser needs: `--share=network`,
   `--share=ipc`, `--socket=wayland`, `--socket=fallback-x11`, `--device=dri`,
   `--socket=pulseaudio`, `--filesystem=xdg-download`. Be ready to explain
   `xdg-download` (downloads are saved there).
5. Use the newest GNOME runtime on the day of submission.
6. Test locally:

   ```sh
   flatpak run org.flatpak.Builder --force-clean --sandbox --user --install \
     --install-deps-from=flathub --repo=repo builddir br.com.bebitterbebetter.browser.Bitter.yml
   flatpak run --command=flatpak-builder-lint org.flatpak.Builder manifest br.com.bebitterbebetter.browser.Bitter.yml
   flatpak run --command=flatpak-builder-lint org.flatpak.Builder repo repo
   ```

7. Open the pull request against `new-pr` with a description you write,
   including the AI disclosure: which parts of the app, packaging and
   documentation were generated or assisted by AI, and roughly how much.
8. Answer the reviewers yourself. Comment `bot, build` to start a test build.
9. After acceptance, accept the invitation to
   `flathub/br.com.bebitterbebetter.browser.Bitter`.
10. Verify the app: flathub.org > Developer Portal > the app > Verification.
    Put the token on its own line in `site/.well-known/org.flathub.VerifiedApps.txt`
    and merge; the *Website* workflow publishes it. An agent may make this
    one-line change in this repository.
11. Add `x-checker-data` to the source so the Flathub bot opens update pull
    requests for each release; review and merge them yourself.

## After Flathub

- Add Flathub to the install table in README, `docs/distribution.md`,
  `packaging/release-install-notes.md` and the website.
- `scripts/install.sh --method flatpak` can then install from Flathub instead
  of the release bundle.
